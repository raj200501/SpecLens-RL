objective and success definition of each task, generated from the environment
code. Layouts are sampled by rejection: start, goal and task objects are placed
uniformly on distinct cells, walls are placed uniformly among the remaining
cells subject to all objects being mutually reachable, and in \PF{} and \GT{}
the goal is at least four steps from the start. In \GT{}, gems are sampled only
from reachable cells $c$ with $d(\text{start},c)+d(c,\text{goal}) >
\text{deadline}$, where $d$ is the shortest-path distance around walls.

\paragraph{Pilot runs and what they changed.} Before the main experiment we ran
single-seed pilots of Oracle and Proxy PPO on every task. They led to three
changes, all made before any main-experiment run, and we list them because they
are researcher degrees of freedom: (i) a multilayer perceptron over the
flattened grid learned the two-stage \ST{} task much more slowly than a small
CNN, so we use the CNN; (ii) deterministic (argmax) evaluation scored well below
the same policies' behavior during training, so we evaluate the stochastic
policy that PPO optimizes; and (iii) with a gem bonus of $0.3$, Proxy PPO on
\GT{} learned the intended behavior and rarely collected gems, so the default
bonus is $0.6$. The pilot code is not part of the repository. The
dose--response sweep revisits the gem bonus: at $\lambda=0.5$ (a bonus of
$0.3$), the \res{sweep-seeds} runs hack in \res{sweep-GemTimeout-0.5-hack-min}\% to
\res{sweep-GemTimeout-0.5-hack-max}\% of episodes, so the single pilot run was
not representative of that bonus.

\paragraph{Compute and provenance.} The \res{n-runs} main and dose--response
runs took \res{cpu-hours} CPU-hours including evaluation and monitor rollouts,
and the \res{pen-n-runs} monitor-penalty runs another \res{pen-cpu-hours}, on a
single 4-core machine with one core per run. Every training run records a
fingerprint of the code, configuration and (for the monitor-penalty runs) the
monitor it was produced with (\texttt{results/runs.csv} and
\texttt{penalty\_runs.csv}), and continuous integration fails if any committed
run does not match the current code. Runs also record the commit, and whether
\texttt{src/} had uncommitted edits, when they finished; some finished while
the repository had uncommitted edits to analysis code that no training run
imports, which the fingerprints confirm. Training is deterministic given a
seed: when we retrained all \res{pen-n-runs} monitor-penalty runs in a fresh
container to add monitor rollouts, we checked that every evaluation episode was
reproduced exactly. Every figure and table, and every result and setting cited
in the text, is rebuilt from the saved results in about two minutes with
\texttt{python -m speclens.report}.

\section{The Exact Proxy-Optimal Policy}
\label{app:optimal}

For one layout, the state of each task is the agent's cell, the time step and
the task's own state: nothing in \PF{}; whether the object is carried and how
many steps remain until the console can confirm again in \ST{}; and the set of
collected gems in \GT{}. We enumerate every state reachable from the start by
stepping the environment itself (not a reimplementation of it), recording each
transition's reward with the channel at scale 1, and solve the finite-horizon
MDP by backward induction over the time step for each channel scale, with the
discount factor $\gamma=\res{gamma}$ that PPO optimizes. The greedy policy,
with ties broken by action order, is then rolled out in the environment to
obtain its hack label, success and true return. Two tests check the solver.
One replays this policy and requires its discounted proxy return to equal the
solver's value of the start state on every task and split. The other compares
the solver's value with an exhaustive search over every action sequence on
short horizons, run on copies of the environment so that it does not depend on
the solver's state definition; we checked that it fails when the console
cooldown or the set of collected gems is removed from the state. The solved
layouts, the first \res{optimal-layouts} ID evaluation layouts of each task,
have \res{opt-ProxyFarming-states-min}--\res{opt-ProxyFarming-states-max}
(\PF{}), \res{opt-SensorTamper-states-min}--\res{opt-SensorTamper-states-max}
(\ST{}) and \res{opt-GemTimeout-states-min}--\res{opt-GemTimeout-states-max}
(\GT{}) reachable states.
